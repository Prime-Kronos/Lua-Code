# Topdim — резервное копирование и восстановление

**Runbook / план. Статус: не исполнен и не протестирован.**

## До production
- Выбрать провайдера в Узбекистане и получить письменное подтверждение физического местонахождения primary DB, replicas, snapshots, WAL/PITR, object storage и журналов.
- Использовать управляемый PostgreSQL, если провайдер предоставляет документированные RPO/RTO, PITR и шифрование.
- Для self-managed PostgreSQL назначить ответственного за обновления, мониторинг, WAL-архивирование, проверку целостности и восстановление.
- Хранить резервные копии в отдельном аккаунте/проекте или отдельной зоне доступа; шифровать до передачи; ограничить доступ отдельной ролью.
- Не хранить дампы, ключи, пароли и реальные пользовательские данные в GitHub или в общедоступных каталогах.

## Минимальная политика для согласования
- Ежедневная полная резервная копия.
- PITR/WAL, если поддерживается и оправдано бюджетом.
- Целевая глубина хранения: 14–30 дней, согласовать с юристом и провайдером.
- Копии фотографий должны резервироваться отдельно от PostgreSQL.
- Ежемесячная проверка восстановления в изолированную тестовую БД.
- Ежеквартальная проверка доступа и процедуры аварийного восстановления.

## Пример ручной проверки PostgreSQL
Выполнять только уполномоченному администратору на тестовом контуре с синтетическими данными:

```sh
pg_dump --format=custom --no-owner --no-acl "$DATABASE_URL" --file=topdim-test.dump
createdb topdim_restore_test
pg_restore --clean --if-exists --no-owner --no-acl --dbname=topdim_restore_test topdim-test.dump
psql topdim_restore_test -c "SELECT COUNT(*) FROM topdim_submissions;"
```

Не выполняйте восстановление поверх production. Команды выше не включают шифрование или удалённую доставку; их нужно добавить в соответствии с возможностями выбранного провайдера.

## Протокол теста восстановления
Записать дату, провайдера, тип копии, длительность восстановления, объём восстановленных данных, ошибки, проверку фотографий и подтверждение удаления тестового окружения. Не отмечать резервное копирование как «проверенное», пока реальное восстановление не завершено.
